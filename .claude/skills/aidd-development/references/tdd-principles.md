# TDD Principles Guide

## Red-Green-Refactor サイクル

TDDの基本サイクル。すべてのエージェントはこのサイクルを厳守する。

### 1. RED - テストを書く（失敗させる）

**原則**: 実装コードを書く前に、必ずテストを先に書く。

- テストは実装が存在しない状態で書く
- テストを実行し、期待通りに**失敗する**ことを確認する
- コンパイルエラーではなく、アサーション失敗であるべき
- 失敗メッセージが意味のあるものであることを確認する

```
Good: "Expected getUser(1) to return {name: 'Alice'}, but got undefined"
Bad:  "Cannot read property 'name' of undefined"
```

**RED確認のチェックリスト**:
- [ ] テストが実行可能な状態である
- [ ] テストが失敗する（FAILする）
- [ ] 失敗理由が「未実装」であり「テストのバグ」ではない
- [ ] テスト名が期待する振る舞いを明確に表現している

### 2. GREEN - テストを通す（最小実装）

**原則**: テストを通す最小限のコードだけを書く。

- 過度に汎用的なコードを書かない
- 「将来必要になるかもしれない」コードを書かない
- テストが通る最もシンプルな実装を選ぶ
- ハードコードでもよい（後でリファクタする）

**GREEN確認のチェックリスト**:
- [ ] すべてのテストがPASSする
- [ ] 新しいテストだけでなく既存テストも通る
- [ ] 実装がテスト要件を満たしている
- [ ] 不必要な機能を追加していない

### 3. REFACTOR - コードを改善する

**原則**: テストが通る状態を維持しながら、コードの品質を改善する。

- 重複の排除（DRY）
- 命名の改善
- メソッドの抽出
- デザインパターンの適用
- テストコードのリファクタも含む

**REFACTORのチェックリスト**:
- [ ] リファクタ前後でテストが通り続ける
- [ ] コードの可読性が向上した
- [ ] 重複が排除された
- [ ] 適切な抽象化レベルになった

## テスト設計原則

### FIRST原則

| 原則 | 説明 |
|---|---|
| **F**ast | テストは高速に実行できる |
| **I**ndependent | テスト間に依存関係がない |
| **R**epeatable | 何度実行しても同じ結果になる |
| **S**elf-validating | テスト自体が合否を判定する |
| **T**imely | テストは実装前に書く |

### Arrange-Act-Assert (AAA) パターン

```
// Arrange: テストの前提条件を準備
const user = createUser({ name: "Alice", age: 30 });

// Act: テスト対象の操作を実行
const result = user.greet();

// Assert: 結果を検証
expect(result).toBe("Hello, I'm Alice!");
```

### テストケースの分類

#### 正常系（Happy Path）
- 期待通りの入力に対して正しい出力を返す
- 最も基本的な使用シナリオ

#### 異常系（Edge Cases）
- 境界値（0, 空文字, null, undefined, 最大値）
- 不正な入力（型の不一致, 範囲外）
- エラー条件（ネットワークエラー, タイムアウト）

#### コーナーケース
- 複数の条件が同時に発生する場合
- 状態遷移の境界
- 並行処理・競合条件

## テストの粒度

### Unit Tests（単体テスト）
- 個々の関数/メソッドの振る舞いをテスト
- 外部依存はモック/スタブで置換
- 実行速度: ミリ秒単位
- カバレッジ目標: 80%以上

### Integration Tests（結合テスト）
- モジュール間の連携をテスト
- DB、APIなど外部リソースを含む場合がある
- 実行速度: 秒単位
- 重要な結合ポイントを網羅

### E2E Tests（エンドツーエンドテスト）
- ユーザー視点でのシナリオテスト
- 実際の環境に近い条件で実行
- 実行速度: 分単位
- 主要なユーザーフローを網羅

**テストピラミッド**:
```
    /  E2E  \        少ない（重要フローのみ）
   /Integration\     中程度（主要結合点）
  /   Unit Tests  \  多い（すべての関数/メソッド）
```

## アンチパターンと回避策

### 1. テストが実装の詳細に依存する
- **問題**: 内部実装の変更でテストが壊れる
- **回避**: 公開インターフェースに対してテストする

### 2. テスト間の依存関係
- **問題**: テストの実行順序で結果が変わる
- **回避**: 各テストでsetup/teardownを適切に行う

### 3. 過度なモック
- **問題**: モックが多すぎて本当の振る舞いをテストできない
- **回避**: 必要最小限のモックに留める

### 4. フレークテスト（不安定なテスト）
- **問題**: 同じコードで通ったり落ちたりする
- **回避**: 非同期処理、時間依存、外部依存を適切に制御する

### 5. テストコードの重複
- **問題**: 同じセットアップが複数テストに散在
- **回避**: テストヘルパー/フィクスチャを活用する
