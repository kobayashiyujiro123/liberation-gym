# AIDD (AI Driven Development) Principles

AI駆動開発の原則とベストプラクティス。全エージェントが参照する基盤ドキュメント。

---

## 核心原則

### 1. 要件定義ファースト

> AI駆動開発の成否は「要件定義の質」で8割決まる。

- コードを書く前に「何を作るか」を徹底的に明確にする
- 曖昧な指示 → AIが推測 → 意図と違う実装 → 手戻り
- 明確な仕様 → AIが正確に実装 → 一発で完成
- 仕様書が真実の源泉（Single Source of Truth）

### 2. Explore → Design → Plan → Code → Commit

Anthropic公式推奨のワークフロー:

```
Step 1: Explore（探索）
  → コードベースを理解する。まだコードは書かない。

Step 2: Design（デザイン）
  → 見た目と操作感を先に決める。

Step 3: Plan（計画）
  → 「think hard」で深く考えさせる。計画をドキュメント化。

Step 4: Code（実装）
  → スプリント単位で小さく実装。

Step 5: Commit（コミット）
  → 満足したら保存。PRを作成。
```

**なぜこの順序が重要か**:
- Step 1-3を省略すると、AIは「間違った問題を解決する」コードを書きがち
- 事前のリサーチと計画が、手戻りを大幅に削減

### 3. ファイルシステムは永続記憶

Planning-with-files原則（Manus設計思想）:

```
コンテキストウィンドウ = RAM（揮発性、制限あり）
ファイルシステム = ディスク（永続、無制限）
→ 重要なことはすべてファイルに書き出す
```

- PRDはファイルに保存
- 設計判断はADRとして記録
- 調査結果はfindings.mdに記録
- 進捗はprogress.mdで追跡

### 4. 小さく作り、こまめに確認

- 全部を一度に作らない
- 3-5日単位のスプリントに分割
- 各タスクは30分〜2時間
- タスク完了ごとにユーザー確認

### 5. 批判的レビューの組み込み

- 別コンテキストで批判的レビューを行う
- 実装者（code-implementer）とレビュアー（code-reviewer）を分離
- 「AIが書いたコードを疑う」観点を常に持つ

## 思考深度制御

Claude固有の機能。複雑な問題には深い思考を促す:

| キーワード | 思考深度 | 使用場面 |
|---|---|---|
| think | 標準 | 一般的な設計判断 |
| think hard | 深い | 複雑なアーキテクチャ決定 |
| think harder | より深い | 難しいバグの原因分析 |
| ultrathink | 最大 | 重大な設計変更、移行計画 |

## 軌道修正の原則

### 早期発見・早期修正
- 2回以上同じ問題で修正したら → /clear して最初から
- 失敗したアプローチがコンテキストを汚染する
- 新しいセッションで仕様ファイルを参照して再開

### 中断・修正ツール
| 操作 | 効果 |
|---|---|
| Esc | 中断（コンテキスト保持） |
| Esc x 2 | 履歴に戻る |
| /rewind | 会話を巻き戻す |
| /clear | コンテキストをリセット |

## コーディング原則

### やるべきこと
- 既存コードのスタイルに従う
- テストを書く
- エラーハンドリングを実装する
- セキュリティを考慮する
- 小さく実装し、こまめにコミットする

### 避けるべきこと
- 要件にない機能を追加する（over-engineering）
- 不要なドキュメント・コメントを追加する
- 使わないコードの「改善」を行う
- 将来の要件を先取りする（YAGNI違反）
- 過度な抽象化やヘルパーの作成

## テスト戦略

### テストピラミッド
```
    /  E2E  \        少ない（主要フローのみ）
   /Integration\     中程度（API・DB境界）
  /   Unit Tests  \  多い（ビジネスロジック）
```

### AIが書いたテストを疑う観点
- テストが要件（PRD）を満たしているか
- 境界条件をカバーしているか
- 偽陽性（常にパスするテスト）がないか
- 偽陰性（本来失敗すべきケースがパスする）がないか
- モックが過剰でないか

## トレーサビリティ

```
PRD → Sprint → Task → PR → Commit
全てをリンクで繋ぐ
```

- PRD: docs/PRD.md
- Sprint: docs/plans/sprint-plan.md
- Task: Sprint内で定義
- PR: タイトルに [Sprint-N] を含める
- Commit: メッセージに Task番号を含める
- ADR: 重要な技術判断を記録

## Multi-Claude活用

### 並列ワークフロー
- 複数のgitチェックアウト/worktreeで並列作業
- 実装者とレビュアーを分離
- 異なるモジュールを同時開発

### コンテキスト分離
- 要件定義と実装は別セッション
- レビューは独立したセッション
- 各セッションは成果物（ファイル）を通じて連携

## アンチパターン

### 1. いきなりコードを書く
- **問題**: 要件が不明確なまま実装 → 手戻り
- **回避**: Explore → Design → Plan を必ず先に

### 2. 大きなタスクを一括実行
- **問題**: コンテキストが溢れる → 品質低下
- **回避**: スプリント分割 + タスク分解

### 3. レビューなしで進める
- **問題**: バグ・セキュリティ問題の見落とし
- **回避**: 別コンテキストでのレビューを必須化

### 4. ファイルに書き出さない
- **問題**: コンテキストが消える → 目標を忘れる
- **回避**: 重要なことは全てファイルに保存

### 5. 失敗したアプローチを繰り返す
- **問題**: 同じ失敗パターンが汚染
- **回避**: 2回失敗したら /clear して仕切り直し
